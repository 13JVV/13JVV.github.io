Problem

위험을 지도에 표시한 다음, 누구를 어디로 보낼지가 비어 있었습니다

현장
후문 일대는 학생 유동인구가 몰리는 동시에, 좁은 골목에 보행자, 차량, 오토바이, PM이 섞입니다.제안서는 후문 삼거리의 교통 환경 변화를 고려해 이동수단이 섞이는 구간의 대응 체계를 검토했습니다.주택가와 원룸촌은 야간 조도가 낮고 인적이 드물어 귀가 불안감이 높은 구역으로 보도됐습니다.
한계
순찰은 고정 경로를 반복하고, 대응은 사고 뒤 처리에 집중돼 있었습니다.인력과 예산을 나누는 객관적 기준이 없어 배분이 경험과 관행에 기대고 있었습니다.
질문
안전 인력이 10명뿐일 때 누구를 어디로 보낼 것인가.정비 예산이 1,000만 원일 때 어느 골목의 가로등부터 고칠 것인가.즉시 움직이는 순찰과 시간을 두고 집행하는 정비를 같은 위험 데이터에서 판단하도록 문제를 정의했습니다.
한계현재 구조결과
정적 순찰고정 경로를 반복하는 방식실시간으로 변하는 위험에 바로 대응하지 못함
사후 대응사고 발생 후 처리에 집중예방적 개입이 없음
근거 부재인력, 예산 배분의 객관적 기준 없음배분이 경험과 관행에 의존

Planning

“무엇을 감지하는가”보다 “어떤 자원을 어떤 시간축으로 나눌 것인가”를 먼저 정했습니다

모든 산출물이 상태, 행동, 결과라는 하나의 의사결정 흐름에 연결되도록 맞췄습니다.

우선순위먼저 정한 질문뒤로 미룬 것
P0 단기 안전지금 어느 구역에 순찰 인력을 보낼 것인가?캠퍼스 전체 확장, 완성형 하드웨어 도입
P1 장기 정비누적 위험 로그를 기준으로 무엇을 먼저 고칠 것인가?예산 집행 자동화, 외부 기관 연동

협업 전공별 제안이 부딪칠 때 회의에서 밀어붙이지 않고, 순찰 경로와 정비 우선순위를 한 화면에 놓은 대시보드 안 두 가지를 직접 만들어 비교했습니다. 팀원들의 전문성이 더 잘 드러나는 안을 채택하고, 제 초기 안을 수정했습니다.

Solution

하나의 위험 판단에서 시간축이 다른 두 조치가 갈라집니다

단순한 앱이 아니라 안전 통합 관제 센터(ICC)의 인프라로 설계했습니다.

위험 상태 (State)CCTV 영상, IoT 센서, 학생 사진 제보, 날씨와 학사 API
↓

  • 현장 경고등 자동 제어

두 트랙을 나눈 이유 순찰은 즉시 움직일 인력을 배정하고, 정비는 반복되는 위험의 원인을 바꾸는 결정입니다. 집행 주기가 다른 두 업무를 나누되, 학생 제보와 순찰 로그를 함께 참조하게 했습니다. 데이터가 쌓이면 정확도가 오른다는 점은 앞으로 검증할 가설입니다.

Architecture

수집, 처리, 실행을 세 계층으로 나눴습니다

Layer 1

데이터 수집

  • Edge AI 카메라가 원본 영상 대신 객체 정보만 보내 네트워크 부하를 줄임
  • mmWave 레이더, 초음파와 IR, 조도, 소음 센서
  • 학생 앱 사진 제보 (불법 주차, 시야 차단, 조명 고장)
  • 기상청 날씨, 학사 일정 API로 시간대와 계절 가중치 산정
Layer 2

전송과 처리

  • 5G, Wi-Fi 6 저지연 통신에 저전력 센서는 LoRa 병행
  • Edge에서 탐지와 필터링, Cloud GPU에서 장기 학습과 정책 최적화
  • Apache Kafka로 객체 메타데이터와 제보 이벤트 전달
  • Spark Streaming 또는 Flink로 실시간 이벤트 처리
  • 장애 시 기본 순찰 정책 유지, Edge 단독 운영 모드
Layer 3

실행과 피드백

  • 순찰대원 앱에 계산한 순찰 경로를 실시간 푸시
  • 관리자 대시보드에 위험 히트맵과 정비 우선순위
  • 임계치를 넘으면 스마트 경고등, 가변 표지판 자동 제어
  • 공유 킥보드 API와 연동한 PM 지오펜싱 감속, 운행 제한
  • 캠퍼스 안내판의 구역별 안전 정보 갱신

계층을 나눈 이유 영상에서 뽑은 객체 정보와 학생 제보는 들어오는 주기와 처리 방식이 다릅니다. 수집과 분석 사이에 큐를 두어 의존성을 줄이고, 연결이 끊겨도 기본 순찰 정책을 유지하는 구조를 제안했습니다. Kafka와 스트림 처리 도구는 설계 후보이며, 부하와 장애 실험은 하지 않았습니다.

Decisions

무엇이, 얼마나 위험하고, 그래서 무엇을 할지 순서대로 정했습니다

모두 개념 설계이며, 모델 학습이나 실측 결과는 아직 없습니다.

위험을 사고 빈도가 아니라 교통공학의 대리 지표로 재기로 했습니다

YOLOv11(또는 YOLOv8)로 보행자, 차량, 오토바이, PM을 검출하고 ByteTrack으로 객체별 이동 경로를 추적합니다.여기서 충돌까지 남은 시간(TTC)과 두 객체가 같은 지점을 지난 시간 차(PET)를 계산합니다.두 값 모두 작을수록 위험한 상황입니다.

수집 지표 보행 밀집도, PM과 오토바이 주행 속도, 불법 주정차 체류 시간

상황 가중치는 제안값으로만 두었습니다

같은 지표라도 개강 시즌이나 비 오는 저녁은 더 위험하다고 보고 가중치를 제안했습니다.실측으로 보정하기 전의 값이라 결과처럼 쓰지 않았습니다.

제안값 개강 시즌과 축제 기간 × 1.4, 우천과 강설 × 1.3, 목요일 저녁 × 1.2 (실측 보정 전)

한 시간 뒤 위험을 예측해 미리 배치하도록 했습니다

LSTM 또는 XGBoost로 수업 종료 시간, 날씨, 요일을 반영해 1시간 뒤 위험도를 예측하는 구조입니다.사고 뒤 대응이 아니라 선제 배치를 하기 위한 장치입니다.

상태 예측 모델 후보만 정했고 학습은 하지 않았습니다

순찰과 정비를 하나의 순차적 의사결정 문제로 묶었습니다

조치가 이후 위험 상태와 가용 자원에 영향을 주므로 PPO 기반 에이전트를 개념 설계했습니다.보상 함수에는 안전 향상, 비용, 대응 시간의 균형을 넣었습니다.단위가 다른 항목의 정규화와 가중치 결정은 남아 있고, 규칙 기반 배분보다 나은지는 같은 시나리오에서 비교해야 합니다.

보상 Reward = w₁ · ΔSafety − w₂ · Cost − w₃ · Response_Time (가중 합만으로 Pareto 최적해를 검증한 것은 아닙니다)
구성내용
State 상태시간대별 유동인구 밀도, PM과 오토바이 주행 속도, 조도 센서 값, 최근 1시간 위험 제보 여부
Action 행동① 인근 순찰 대원에게 이동 명령 ② 위험 구간 조명 밝기 상향 ③ PM 업체 서버 연동 감속 지오펜싱 ④ 정비 대상 등록 (장기 트랙으로 이관)
Reward 보상TTC, PET 개선량, 위험 신고부터 현장 조치까지 걸린 시간의 단축 정도

2. 반복 생성시나리오 매트릭스, 상태와 행동 타입, 대시보드 표와 문구, SUMO 대조군과 실험군 체크리스트PPO의 상태, 행동, 보상 정의와 가중치 설계 기준 결정. 실제 값은 검증 뒤 보정
3. 일관성 검증아키텍처 입력이 PPO 상태에 빠짐없이 연결되는지, 대시보드 지표가 결과 지표와 맞는지 diff로 점검측정 전 수치를 성과처럼 쓰지 않기, 예시 UI 값과 시뮬레이션 결과를 분리

에이전트가 낸 상태, 행동, 보상 후보는 바로 채택하지 않고, 후문 생활권의 도로와 시설 맥락에 맞는지 제가 판정했습니다. 이 과정은 개념 설계를 위한 작업이며, PPO 학습이나 SUMO 실행 성과를 뜻하지 않습니다.

Q2

위험 점수가 현실을 반영하는가

TTC, PET, 조도, 제보의 실측 보정과 시간대별 오탐, 누락 검토가 필요합니다. 상황 가중치는 현재 제안값입니다.

Q3

현장에서 실행할 수 있는가

인력, 예산 제약, PM 사업자 연동 가능성, 운영자 승인 기준, 개인정보 처리와 장애 대응을 검토해야 합니다.

성과 수치의 범위 사고 감소와 비용 절감은 후속 실험에서 확인해야 할 목표이며, 이 페이지에서 주장하지 않습니다.
